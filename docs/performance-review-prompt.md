# Web 性能审查提示词（访问速度 / 加载速度 / 并发）

> 用途：让 AI 对代码做一次聚焦 Web 性能的深度审查，输出可直接落地的优化方案。
> 适用范围：前端（React/Vue 等）+ 后端（API 服务）+ 部署层（nginx/CDN）全链路。
> 版本：v1.0（2026-08-10）

---

## 使用说明

1. **填写尖括号内的变量**：文件路径、技术栈、基线数据、目标场景，这几行决定结论是「真问题」还是「伪优化」，务必认真填。
2. **范围聚焦**：本提示词只查三个维度（访问速度 / 加载速度 / 并发能力），渲染冗余、内存泄漏、业务 BUG 等**不在范围内**，除非它们直接构成上述瓶颈的根因。
3. **首轮输出**：如嫌一次太长，可在提示词末尾追加「先给摘要表，若存在高严重度项再展开对应章节」。
4. **后续复用**：换仓库/换文件时，只改【项目上下文】部分即可。

## 完整提示词

```
深度审查以下范围：<文件/目录路径>（只读审查，只输出报告，不要修改代码）

【项目上下文】
- 技术栈：<如 React 19 + Vite + TypeScript / FastAPI + SQLAlchemy + SQLite / nginx 静态部署>
- 部署形态：<如前端静态文件走 nginx，后端 uvicorn 单进程，DB 为 SQLite>
- 已知基线：<如首屏 ~2s、bundle ~1.8MB、任务状态 3s 轮询、后端并发任务上限 3>
- 目标场景：<移动端弱网优先 / 桌面端优先 / 二者兼顾>

【审查目标】
只聚焦以下三个维度。其他问题（渲染冗余、重复渲染、内存泄漏、业务逻辑 BUG）本次不查，
除非它们直接构成下述瓶颈的根因，否则不要展开。

1. 访问速度（接口链路）
   - 串行请求改并行（Promise.all）、请求依赖链分析、首屏关键数据聚合
   - TTFB 归因：DB 慢查询、缺索引、N+1、接口响应体过大
   - 轮询频率与策略（本项目任务状态 3s 轮询：是否可降频 / 按需触发 / 长连接替代）
   - 缓存策略：HTTP 缓存、前端状态缓存、已失效请求的取消

2. 加载速度（资源传输）
   - bundle 体积：代码分割（React.lazy）、tree-shaking、未使用依赖清理
   - 传输压缩：gzip/brotli 是否开启、Cache-Control/ETag 配置、CDN 使用
   - 图片：格式（webp/avif）、尺寸、懒加载；字体加载策略；preload/prefetch

3. 并发能力（吞吐与稳定性）
   - 前端：重复请求去重、并发数限制、请求合并、AbortController 取消
   - 后端：任务队列并发上限、DB 写锁竞争（SQLite）、连接池、线程池、限流

【方法要求】
- 每条结论必须有证据：file:line + 关键代码片段；无证据的判断一律不输出
- 能实测的必须实测（Chrome trace / Lighthouse / Network 瀑布流 / 后端日志 / 压测），
  实测数据优先于静态推测
- 上下文不足时：基于合理假设继续，在报告开头列「假设清单」；
  仅当假设会根本改变结论时才提问（≤3 个）

【输出格式】
- 第一部分 · 摘要表：问题 | 维度 | 严重度(高/中/低) | 位置 | 预估收益 | 修复成本，
  按收益/成本比排序
- 第二部分 · 每个问题固定六段：
  1. 问题与影响（对用户可感知的速度影响，几句话）
  2. 证据（file:line + 代码 + 实测数据）
  3. 根因
  4. 修复方案（最小 diff 的示例代码，可直接复制）
  5. 收益对比（量化数字：如 TTFB 800→200ms、LCP 2.1→1.3s、bundle 1.8→1.1MB、
     请求 40→12 次、QPS 上限提升；标注估算依据 + 置信度）
  6. 验证方法（具体工具 + 通过标准，如「Lighthouse Performance ≥ 90」、
     「接口 p95 < 500ms」「100 并发压测无 5xx 且无 database is locked」）
- 第三部分 · 执行清单：一页纸，按收益/成本比排序，可直接当 todo 使用

【约束】
- 同一根因的多个表象合并为一条，不凑数
- 不列「潜在的」未证实问题
- 禁止空泛理论，收益必须量化到数字
```

## 三个维度的验证方法配套

| 维度 | 验证工具 / 方法 | 通过标准示例 |
|---|---|---|
| 访问速度 | Chrome DevTools trace（TTFB/接口耗时归因）、后端 slowlog / 查询日志、脚本压测接口 p95 | 接口 p95 < 500ms；首屏 < 1.5s |
| 加载速度 | Lighthouse、bundle analyzer、Network 面板（缓存命中 `from disk cache` 占比） | Lighthouse Performance ≥ 90；总字节数下降 ≥ 30% |
| 并发能力 | k6 / locust 压测（观察队列深度、5xx 率）、SQLite `database is locked` 报错计数 | 100 并发无 5xx、无锁冲突；QPS 提升 ≥ 50% |

## 常见填坑提示

- **基线数据别省**：「列表只有 10 条数据」和「列表 10000 条」的审查结论完全不同，不填基线 AI 只能瞎猜。
- **首屏是交汇点**：首屏耗时 = 资源加载 × 接口返回，归因时按链路拆开，不要糊在一起。
- **输出太长**：追加「先给摘要表，再按严重度展开」即可分轮交付。
