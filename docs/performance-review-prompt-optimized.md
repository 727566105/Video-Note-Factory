# Web 性能审查提示词（优化版：访问速度 / 加载速度 / 并发）

> 用途：让 AI 对代码、构建产物和部署配置进行一次可验证、可复现、聚焦 Web 性能的深度审查，并输出可直接落地的优化方案。
> 适用范围：前端（React/Vue 等）+ 后端（API 服务）+ 部署层（nginx/CDN/容器）全链路。
> 版本：v2.0（2026-08-10）
> 原则：实测优先；代码模式只能证明风险，不能单独证明性能瓶颈。

---

## 使用说明

1. **填写尖括号内的变量**：审查范围、技术栈、部署形态、基线数据、测试口径和目标场景会直接影响结论可靠性。
2. **先确认可审查范围**：若缺少构建配置、部署配置、可运行环境、测试账号或基线数据，必须在报告开头标为“未审查”或“待验证”，不能默认存在或缺失。
3. **范围聚焦**：本提示词只审查访问速度、加载速度、并发能力。渲染冗余、内存泄漏、业务 BUG 等不在范围内，除非它们是上述性能瓶颈的直接根因。
4. **区分事实与预估**：已实测结论必须附环境、方法和结果来源；尚未实施修复时，只能给出带依据与前提的区间或比例预估，禁止编造优化后的绝对数值。
5. **分轮输出**：如首轮输出过长，可在提示词末尾追加“先给摘要表；仅展开高严重度问题；待验证项只列清单”。
6. **后续复用**：换仓库或换审查范围时，至少更新 `【项目上下文】`、`【测量口径】` 与 `【目标场景】`。

## 完整提示词

```text
深度审查以下范围：<文件/目录路径>（只读审查，只输出报告，不要修改代码、配置或数据）

【项目上下文】
- 技术栈：<如 React 19 + Vite + TypeScript / FastAPI + SQLAlchemy + SQLite / nginx 静态部署>
- 部署形态：<如前端静态文件走 nginx，后端 uvicorn 单进程，DB 为 SQLite；是否有 CDN、负载均衡、多实例>
- 已知基线：<如首屏 LCP ~2s、bundle ~1.8MB、任务状态 3s 轮询、接口 p95 ~700ms、后端并发任务上限 3；未知则写“未测”>
- 目标场景：<移动端弱网优先 / 桌面端优先 / 二者兼顾>
- 关键用户路径：<如未登录访问首页 → 登录 → 打开任务列表 → 创建任务 → 查看任务状态>
- 性能目标 / SLO：<如首页 LCP ≤ 2.5s、关键接口 p95 < 500ms、100 并发下 5xx = 0；未定义则写“未定义”>

【测量口径】
- 测试环境：<生产 / 预发 / 本地；部署地区；是否经过 CDN、反向代理、WAF；是否登录>
- 设备与浏览器：<如 Moto G Power 模拟 + Chrome 版本 / MacBook + Chrome 版本>
- 网络条件：<如 Fast 4G / Slow 4G / 不节流；RTT、下行带宽、上行带宽>
- 缓存状态：<冷缓存 / 热缓存；是否清除浏览器缓存、Service Worker、IndexedDB；是否命中 CDN>
- 采样规则：<如 Lighthouse 运行 5 次取中位数；接口请求至少 100 次；压测预热 30s、持续 3min>
- 并发模型：<如恒定 100 VU / 50 RPS 到达率；读写比例；鉴权方式；是否包含文件上传或第三方调用>
- 指标口径：<LCP、INP、CLS、TTFB；接口 p50/p95/p99；QPS、错误率、队列深度、CPU、内存、DB 锁冲突>

【审查前置盘点】
先列出实际访问或审查到的内容，并明确未覆盖部分：
- 前端：入口、路由、数据请求层、状态缓存、构建配置、依赖清单、构建产物；
- 后端：服务入口、路由、中间件、异步任务、数据库访问层、第三方服务调用；
- 部署：Dockerfile、docker-compose、nginx/反向代理、CDN、CI/CD、运行参数；
- 测试条件：可运行命令、测试账号、种子数据、可用日志、压测权限；
- 未提供、无权限访问或无法安全复现的内容必须标记为“未审查”，不得据此推断配置存在或缺失。

【审查目标】
只聚焦以下三个维度。其他问题（渲染冗余、重复渲染、内存泄漏、业务逻辑 BUG）本次不查，
除非它们直接构成下述瓶颈的根因，否则不要展开。

1. 访问速度（接口链路）
   - 首屏和关键用户路径的请求依赖图：串行请求、可并行请求、关键数据聚合、瀑布流阻塞；
   - TTFB 与尾延迟归因：排队、应用处理、DB 查询、第三方依赖、响应传输；
   - DB：慢查询、缺索引、N+1、事务范围、分页、响应体过大、序列化开销；
   - 轮询：频率、退避、页面隐藏时暂停、任务完成后停止、失败重试、长连接替代的适用性；
   - 缓存：HTTP 缓存、前端状态缓存、服务端缓存、缓存击穿、失效请求取消；
   - 网络与协议：HTTP/2 或 HTTP/3、keep-alive、TLS 终止位置、CORS preflight、连接复用。

2. 加载速度（资源传输与关键渲染路径）
   - bundle：按路由/功能拆包、动态导入、tree-shaking、重复依赖、未使用依赖、source map 发布策略；
   - 关键渲染路径：阻塞渲染的 CSS/JS、首屏路由 chunk、首屏数据与关键资源之间的依赖；
   - 传输与缓存：Brotli/gzip、Cache-Control、ETag、immutable 资源、HTML 缓存策略、CDN 命中；
   - 图片与媒体：尺寸、响应式图片、webp/avif、懒加载、首屏图片优先级、视频封面与预加载策略；
   - 字体：字体子集、font-display、预加载、回退字体、跨域加载；
   - 第三方资源：统计、客服、验证码、广告、地图等脚本是否阻塞首屏或引入额外长任务。

3. 并发能力（吞吐、尾延迟与稳定性）
   - 前端：重复请求去重、请求合并、并发数限制、AbortController 取消、超时、重试退避、幂等；
   - 后端：任务队列并发上限、队列容量和背压、线程池/进程数、连接池、限流、超时和取消传播；
   - 数据库：SQLite 写锁竞争、事务粒度、连接生命周期、迁移/批量写入、读写比例；
   - 缓存与多实例：缓存击穿、热点 key、请求合并、共享状态、会话粘性、横向扩容限制；
   - 压测稳定性：p95/p99、排队长度、5xx、超时、重试放大、资源饱和点与恢复能力。

【证据与实测规则】
- 每个“已成立问题”必须至少包含一项可定位证据：`file:line`、关键配置、构建产物清单、网络瀑布图、Trace、日志或压测结果。
- 每条证据都标注类型：代码证据 / 配置证据 / 构建产物证据 / 浏览器实测 / 服务端日志 / 压测结果 / 调用链推导。
- 按证据强度分级，并在每个问题中标明最高等级：
  - A 级（直接证据）：浏览器实测、Trace、服务端日志、APM 指标、压测结果或可复现的响应头/网络瀑布图；可直接证明真实运行环境中的时延、体积、错误率、排队或资源饱和；
  - B 级（完整推导证据）：构建产物、部署配置、完整请求/调用链、数据库执行计划或依赖关系；必须能说明从根因到用户路径影响的完整链路，才可作为“已成立问题”证据；
  - C 级（风险信号）：代码模式、单点静态推断或不完整调用链；只能证明风险，只能进入“待验证观察项”。
- 多条证据并存时按最高等级标记，但低等级证据不能覆盖或抵消高等级实测结果；证据相互冲突时，优先采用同一测量口径下最新、可复现的 A 级证据，并说明冲突原因与待补充验证。
- 代码模式只能证明风险，不能单独证明已造成用户可感知瓶颈；除非能以调用链、依赖关系、构建产物、瀑布图、日志或压测结果佐证实际影响。
- 对当前环境中可安全、无副作用复现的问题，必须实测。实测必须写明：环境、设备/网络、缓存状态、命令或操作步骤、样本量、原始结果。
- 依赖生产权限、账号、外部服务、真实用户数据或高压压测许可的问题，列为“待验证观察项”，并提供可执行的复现步骤、所需权限/数据、观测指标和通过阈值。
- 禁止把未执行的命令、无法访问的日志、未启动的服务或推测性结果写成“实测”。
- 上下文不足时，先在报告开头列“假设清单”；仅当缺失信息会根本改变结论时才提问，最多 3 个问题。

【问题成立、严重度与收益规则】
- 没有足够证据证明影响的项，不进入“问题摘要表”和“执行清单”；仅可列入“待验证观察项”。
- 同一根因的多个表象合并为一项，避免按文件或接口重复计数。
- 严重度按“影响范围 × 发生概率 × 用户可感知程度”判定：
  - 高：已实测影响核心路径，或在目标并发下产生 5xx、超时、明显排队、数据库锁冲突、数据一致性风险；
  - 中：影响高频路径，且证据表明会在常见弱网、中低端设备或常见并发下造成可感知退化，但核心功能仍可用；
  - 低：收益有限、仅在边缘条件触发，或主要改善带宽/成本而非可感知速度。
- 收益必须区分数据来源：
  - 已实测：写“优化前实测值 → 优化后实测值”，并注明测试环境、样本量和指标口径；
  - 静态推导：只能写明确机制支撑的区间或比例，例如“减少 1 个串行往返；在 RTT 150–300ms 的目标网络下，关键等待时间理论上可降低约 150–300ms”；
  - 行业经验估算：仅在无法静态推导时使用，必须标明适用前提与低/中置信度。
- 禁止虚构未实施优化后的 LCP、TTFB、bundle、QPS 或错误率绝对数值。

【输出格式】
第一部分 · 审查范围与假设
- 实际审查范围、未审查范围、可用测试条件、假设清单、基线与测量口径。

第二部分 · 已成立问题摘要表
| 问题 | 维度 | 严重度 | 位置 | 证据类型 | 验证状态 | 预估收益 | 修复成本 |
|---|---|---|---|---|---|---|---|
按收益/成本比排序。验证状态只能是：已实测 / 已由构建或配置确认 / 已由调用链确认。

第三部分 · 每个已成立问题固定六段
1. 问题与影响：说明对哪个用户路径、哪些用户和哪个速度指标造成影响；
2. 证据：给出 `file:line`、关键代码或配置片段，以及实测数据或推导链路；
3. 根因：解释从根因到用户可感知性能退化的完整链路；
4. 修复方案：给出最小 diff 的示例代码或配置，可直接复制；明确兼容性、缓存失效和回滚注意点；
5. 收益对比：写数据类型（实测 / 静态推导 / 行业经验估算）、优化前后数据或预估区间、估算依据、前提条件与置信度；
6. 验证方法：给出具体工具、命令或操作步骤、测试条件、观测指标与通过标准。

第四部分 · 待验证观察项
- 不标严重度，不计入问题数量，不进入执行清单；
- 每项使用固定格式：观察到的风险信号 | 还缺什么证据 | 复现步骤 | 所需权限/数据 | 观测指标 | 通过/失败阈值。

第五部分 · 执行清单
- 只列已成立问题；按收益/成本比排序；
- 每项包含负责人建议（前端 / 后端 / 运维）、预计改动范围、验证项与回滚条件；
- 将需要先补测量基线或补权限的事项标记为前置依赖。

【约束】
- 不列“潜在的”未证实问题；未验证风险必须进入“待验证观察项”。
- 不输出空泛理论，不用“建议优化”“可能变快”等没有机制、证据和验证方式的表述。
- 不因代码风格、抽象偏好或非关键微优化判定性能问题。
- 示例阈值必须结合项目 SLO；若项目未定义 SLO，明确标注为“建议阈值”，不能当作既定验收标准。
```

## 三个维度的验证方法配套

> 下列数值为示例，必须按项目 SLO、用户地域、终端能力和业务峰值替换。所有对比均应使用相同环境、网络和缓存口径。

| 维度 | 验证工具 / 方法 | 最小测试条件 | 通过标准示例 |
|---|---|---|---|
| 访问速度 | Chrome DevTools Network / Performance Trace、服务端访问日志与慢查询日志、接口压测 | 冷缓存与热缓存各测一次；关键接口至少 100 个样本；记录 p50/p95/p99 | 首屏关键接口 p95 < 500ms；TTFB < 800ms；无未解释的串行阻塞 |
| 加载速度 | Lighthouse、WebPageTest、bundle analyzer、Network 面板、构建产物清单 | 固定设备与网络；Lighthouse 至少 5 次取中位数；分别记录冷/热缓存 | 目标设备 Lighthouse Performance ≥ 90；LCP 达到项目 SLO；总传输字节数下降 ≥ 30%（如该项是目标） |
| 并发能力 | k6 / locust / wrk、应用指标、队列指标、DB 锁冲突与资源监控 | 明确 VU/RPS、预热时长、持续时间、读写比和数据规模；压测环境不得影响生产 | 目标并发下 5xx = 0；接口 p95 达标；无 `database is locked`；队列不持续增长且停止压测后可恢复 |

## 常见误区与填坑提示

- **没有基线就没有“提升”**：未测量时只能描述风险机制、预期区间和验证方案，不能声称性能已提升多少。
- **平均值不能代表体验**：接口均值很低但 p95/p99 很高时，用户仍会明显感觉卡顿；关键路径优先看尾延迟。
- **冷缓存与热缓存必须分开**：资源压缩、CDN、HTTP 缓存、Service Worker 的收益只在特定缓存状态下成立。
- **首屏应按依赖图归因**：首屏耗时不是单一数字；应拆分 HTML、关键 CSS/JS、图片/字体、关键接口和客户端处理阶段。
- **压测必须描述模型**：只写“100 并发”没有意义；至少说明到达率或 VU、持续时间、读写比例、数据规模和预热方式。
- **不要把配置缺失当事实**：没有拿到 nginx、CDN 或生产启动参数时，只能说“未审查”，不能断言未开启 Brotli、缓存或多进程。
- **避免为了凑项而微优化**：同一根因合并，低收益且不可感知的改动不应排在关键链路、尾延迟和稳定性问题之前。
