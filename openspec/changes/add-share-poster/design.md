## Context
当前前端已经引入 `html2canvas`，并存在 `ExportImageDialog` 用 iframe 渲染 HTML 后截图导出长图。分享海报可以复用这条路径，同时增强模板、二维码和分享动作。

## Goals
- 让用户在笔记详情页一键生成社交分享海报。
- 海报视觉应更像精心设计的社交卡片，而不是普通截图。
- 操作闭环包含预览、风格选择、保存图片、系统分享、复制链接。

## Non-Goals
- 不在本次实现公开访问的后端分享页。
- 不新增数据库字段或服务端持久化分享记录。
- 不生成多页长图；海报内容以摘要/摘录为主，保证视觉质量。

## Decisions
- Decision: 前端生成海报图片。
  - Why: 项目已有 `html2canvas`，无需新增后端渲染依赖；用户点击分享后可立即预览。
- Decision: 分享链接优先使用当前笔记详情页 URL。
  - Why: 当前项目已有详情页路由，先满足复制和二维码需求；后续如需要公开匿名访问，可另开后端分享页能力。
- Decision: 二维码使用轻量 SVG/Data URL 生成函数或纯前端二维码库。
  - Why: 海报内必须可扫描；若引入新依赖，应选择体积小、浏览器可用的实现。
- Decision: 海报模板固定画布比例。
  - Why: 社交平台海报需要稳定视觉效果，建议默认 `1080 x 1440`，小红书可偏竖版，B 站可偏横向视觉但仍输出竖版海报。
- Decision: 风格库使用配置化 preset。
  - Why: B 站、小红书、YouTube、X、微信公众号、专业简约等风格共享同一渲染管线，但各自需要不同的色彩、装饰、徽标语气、封面处理和内容密度；配置化可以继续扩展新风格。

## Risks / Trade-offs
- Cross-origin 封面可能污染 canvas。
  - Mitigation: 使用现有 `/api/image_proxy?url=...` 代理封面；失败时降级为风格化占位封面。
- Web Share API 不一定可用。
  - Mitigation: 不可用时提供保存图片和复制链接的明确反馈。
- 长笔记直接塞入海报会影响美观。
  - Mitigation: 仅展示清洗后的前若干段/要点，并在底部用二维码链接承接完整内容。

## Migration Plan
无需数据迁移。新增组件和入口后，原有复制、导出、删除等操作保持不变。
